# 配置体验与性能审计报告

日期：2026-03-14

范围：
- `yglue-runtime`
- `yglue-runtime-spring-boot3`
- `yglue-idea-plugin`
- `yglue-orchestrator-ui`
- `yglue-orchestrator`

## 1. 结论摘要

当前项目在“分支执行、动态入参、运行时主链路”上已经具备可用闭环，代码和测试均能支撑核心能力。

但如果从“给最终配置用户是否方便”和“系统性能边界是否清楚”两个角度看，现状更准确的判断是：

- 核心能力：可用
- 配置体验：中上，但复杂场景仍偏工程化
- 性能基线：合理，适合业务编排，不适合当作高并发并行 DAG 引擎
- 代码上报边界：不需要上报全部本地代码才能支持分支和入参配置；代码快照主要用于脚本高级补全

## 2. 重点回答

### 2.1 是否必须上报全部本地代码？

不是。

更准确地说：

- 分支配置、动态入参配置、服务签名展示、REST request/response schema，主要依赖 IDEA 插件导出的元数据。
- 平台脚本编辑器中的项目类补全、`import` 补全、类成员补全，才依赖代码快照。

因此：

- `metadata upload` 是基础能力依赖。
- `code snapshot upload` 是增强能力依赖。

### 2.2 如果不上传全部本地代码，分支和入参如何快速补齐？

应依赖以下数据源：

- 服务元数据：参数名、参数类型、返回类型、说明
- REST schema：`request.path`、`request.query`、`request.body`、`response`
- flow 内上下文：`tempPlans`、上游节点输出 `as/contextKey`
- 系统保留变量：`ctx`、`request`、`input` 等

只要平台把这些数据源聚合好，就足以支持：

- 分支左值/右值快速选择
- 动态入参路径补齐
- 参数说明、类型、必填提示
- 上下游字段引用

代码快照只需要承担：

- 脚本编辑器里的类名补全
- `import` 补全
- 类成员补全

## 3. 现状审计

### 3.1 配置体验

当前前端已经具备较好的基础结构：

- 服务签名摘要：`ServiceNodeConfig.vue`
- 参数构造编辑器：`ParamPlanBuilder.vue`
- 快速/高级模式：`ParamPlanBuilder.vue`
- 提交前快速体检：`ParamPlanBuilder.vue`
- 脚本编辑器补全：`ScriptEditor.vue`

但复杂场景下，配置体验仍然偏工程化。

#### 复杂场景示例 1：嵌套对象入参

例如目标方法签名：

```java
createOrder(CreateOrderCommand command)
```

而 `command` 里包含：

- `command.user.id`
- `command.items`
- `command.ext.couponCode`

如果这些值分别来自：

- `request.body.userId`
- 上游节点返回结果
- 临时变量补数结果

那当前用户需要理解：

- `argPlans`
- `tempPlans`
- `typeHint`
- `listPipeline`
- `resultPath`

能力上能做到，但不够轻。

#### 复杂场景示例 2：多来源分支判断

例如：

```text
request.body.amount > 1000
&& temp.riskLevel == 'HIGH'
&& ctx.creditApproved == true
```

这个场景在业务上常见，但如果用户还需要先定义临时变量，再写条件树，再确认每个值来自哪里，配置体验会迅速进入“半编码”状态。

#### 复杂场景示例 3：补数后再组装入参

例如：

- 先调用内部服务拿客户等级
- 再调用 HTTP 接口拿营销标签
- 最后把两部分补到下游服务入参中

这类场景当前主要通过：

- `serviceCall`
- `httpCall`
- `tempPlans`
- `listPipeline`

完成。表达能力足够，但对普通配置用户不够友好。

### 3.2 性能

当前性能结构的优点：

- Flow 定义有缓存
- 服务方法反射查找有缓存
- `comp.configJson` 解析有缓存
- SpEL 表达式有缓存
- Groovy 脚本编译有缓存

这意味着：

- 重复执行同一条 flow 时，不会每次都重新做完整解析
- 表达式和脚本场景至少有基础缓存，不是纯裸执行

当前性能结构的主要边界：

- DAG 执行器是确定性顺序调度，不是自动并行调度
- service 节点依赖反射调用
- script/expr 节点有解释执行成本
- HTTP 补数节点是同步阻塞式调用

因此系统更适合：

- 接口接管
- 业务编排
- 中等复杂度流程

不适合直接定位成：

- 高并发并行图计算引擎
- 大量外部 IO 并发编排引擎

## 4. 是否需要增加并行执行

当前结论：不建议默认增加并行执行。

原因：

- 业务编排节点经常带副作用
- 节点顺序经常具有业务语义
- 自动并行会显著增加异常传播、事务边界、上下文一致性复杂度
- 现阶段瓶颈大概率在外部 HTTP、脚本、服务调用，而不是调度循环本身

更合理的策略是：

- 当前保持顺序调度
- 先补耗时观测
- 后续如果出现明确场景，再引入“显式并行能力”

不建议做的事情：

- 自动并行所有可执行后继节点
- 在没有节点副作用模型的前提下引入隐式并发

建议未来的正确演进方向：

- 新增并行节点或 fork/join 网关
- 只允许显式声明的无依赖节点并行
- 保持默认执行模型可预测

## 5. 分支与入参的补齐方案

建议把补齐分成两层。

### 5.1 基础补齐：不依赖代码快照

来源：

- 服务元数据
- request schema
- response schema
- tempPlans
- 上游输出别名

支持能力：

- 目标参数名补齐
- 参数类型提示
- 参数说明提示
- `request.path/query/body` 字段选择
- branch 左值/右值字段选择
- `ctx/temp/upstream` 可用字段展示

这是分支和动态入参配置的主路径。

### 5.2 高级补齐：依赖代码快照

来源：

- 项目公开类
- 选定 Jar 元数据

支持能力：

- 脚本编辑器 `import` 补全
- 类名补全
- 成员方法补全
- 字段补全

这是脚本开发增强路径，不应反向变成基础配置前提。

## 6. 配置体验改造建议

### P0

1. 自动生成入参映射草稿

- 根据服务签名和 request schema 自动生成默认 `argPlans`
- 同名优先匹配 `request.path/query/body`
- 其次匹配上游输出和同名 temp 变量

2. 路径选择器替代手填路径

- 用树形数据源替代主要的手写路径
- 手填保留为高级入口

3. 分支条件构建器默认化

- 默认用条件构建器
- 表达式作为高级模式

4. 参数卡片补充说明信息

- 展示参数类型
- 展示参数说明
- 展示必填信息
- 展示默认映射建议

5. 明确区分“元数据上传”和“代码快照上传”

- 文案和入口都要明确
- 避免用户误判“为什么配置能用但脚本补全不全”

### P1

1. 复杂场景模板化

- 请求映射模板
- 补数后调用模板
- 审批分支模板

2. 统一数据来源面板

- request
- temp
- upstream outputs
- globals

3. 类型驱动 UI

- `List<T>` 自动进入列表映射器
- object 自动进入字段映射器
- scalar 只显示简单来源选择

4. 快速体检增强

- 分支永不命中风险
- 类型可转换风险
- 未使用 temp 变量
- HTTP 节点缺超时/重试

### P2

1. 示例数据驱动预览

- 给定示例 request
- 实时预览 branch 命中
- 实时预览入参组装结果

2. 节点级上下文可视化

- 展示当前节点执行前可用上下文
- 降低用户对系统变量的猜测成本

3. 脚本补全能力分层

- 基础补全：metadata/schema
- 高级补全：code snapshot

## 7. 产品边界建议

建议正式定义为：

- `yglue-runtime`：只负责加载本地规则并执行
- IDEA 插件：负责元数据上报、代码快照上报、规则同步
- 平台：负责展示、编排、辅助补全、管理

并且明确：

- 分支和动态入参配置能力不能依赖代码快照才能成立
- 代码快照只为脚本体验增强服务

## 8. 最终判断

当前项目已经可以支撑：

- 分支配置与执行
- 动态入参配置与执行
- 平台化编排
- 插件同步到本地项目执行

但如果目标是“让不懂运行时实现细节的配置用户也能低门槛完成复杂编排”，还需要继续做配置产品化。

一句话总结：

- 现在的系统已经“能用”
- 下一阶段要做的是让它“更好配、更少猜、更少手填”
